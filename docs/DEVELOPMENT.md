# DX-RAG 共享开发指南

本指南是产品开发的共同入口。Codex 与 Claude Code 的根目录指引均应先引导执行者阅读本文件，再阅读与当前任务相关的代码、规格和测试。遵守适用的系统、工具和权限约束，在此基础上遵循用户当前指令；明确的本次指令不因历史文档中较早的任务顺序而失效。

## 当前方向与文档分工

DX-RAG 是以文档摄入、知识库管理、检索问答和来源展示为核心的知识库应用。当前产品开发在保留 V1 已有能力和主线前端优化的基础上，围绕用户体验和可靠性迭代。流式回答已实现，并使用虚构资料在隔离知识库中验证真实检索、DeepSeek 和浏览器；真实用户资料及辅助技术未参与验收，后续以当前代码与任务记录为准。

- [README](../README.md)：面向使用者的项目介绍、启动方法与已实现功能；具体实现以当前代码和验证为准。
- 产品功能文档（可放在 `docs/features/`）：记录该功能的目标、范围、设计决定、验收标准和任务进展。按任务需要建立，不预先假设尚未确定的设计已批准或已实现。
- [V1 SPEC](SPEC.md) 与 [V1 TASKS](TASKS.md)：已发布 V1 的历史规格和任务记录。V1 当时未包含的功能不是对未来产品开发的永久禁止；新行为应有明确需求和合适验证。
- [V2 入口](v2/README.md)、[V2 SPEC](v2/SPEC.md) 和 [V2 TASKS](v2/TASKS.md)：V2 评估及相关实验的范围、协议、任务和历史记录。阅读其中的“当前”、批准、顺序与权威层级时，应结合记录日期和实验范围；不把该实验路线自动作为普通产品功能的前置条件。
- [原 CLAUDE 工作流历史副本](../CLAUDE.legacy-v2.md)：原 `CLAUDE.md` 的完整原字节副本，保留其记录时点的规则与状态，供明确处理相关 V2 历史或实验时参考；它不是普通产品任务的当前全局指令。

本产品分支基于本地 `main`，包含已合入的 Phase 20 评估材料。Phase 21 实验成果保存在独立实验分支及工作区，不因此视为已合入本分支。不要把不同分支或不同时点的状态、证据与批准混为一谈。

## 协作与变更

1. 先理解用户目标、现有行为和工作区状态；对需要共同决策的产品行为说明选项、影响和尚未确定之处。用户要求先讨论或只做设计时，遵循其范围。
2. 用与复杂度相称的方式记录需求、设计和验收。完成当前任务所需的检查和实现；不因为历史 V2 的 Phase 顺序自动启动或阻止无关的产品功能。
3. 保持修改聚焦。保护既有用户修改和工作区；不擅自清理、重建或覆盖本地上传、ChromaDB、模型、配置和历史实验材料。
4. 保持现有 API 和数据语义，除非任务明确要求改变；确有变化时说明兼容影响并验证。`file_id` 是文件身份，`chunk_id` 是切片身份，不互换。上传失败回滚、部分 OCR 警告等现有行为需要在相关改动中维持或明确设计与验证变化。
5. 对每项变更运行必要且相称的检查，并审阅 diff；说明改动、验证结果和限制。区分真实服务、离线、模拟与历史结果，不把模拟结果描述成真实端到端验证。
6. 尊重已冻结的历史资料、实验输入、证据与批准记录；不要为了新产品方向改写过去结论。涉及既有 V2 评估或实验时，阅读其适用的 SPEC、任务、协议与证据，遵守对应范围。
7. 根据用户意图和适用的 Git 约定处理分支；不擅自提交、合并、创建或移动标签、重写历史，或丢弃用户改动。

## 安全与运行边界

- API 密钥只通过后端环境变量或本地配置提供，不写入源码、前端、日志、截图或版本库。
- 上传文件名的路径穿越校验等现有安全边界不可因普通功能改动而放松。检索到的文档内容不应被当作高优先级指令；提示词层面的防护不是完整安全保证。
- V1 面向本地或可信网络，现有版本没有用户认证和授权；CORS 不能替代访问控制。
- 使用 DeepSeek 问答时，问题、对话历史和检索上下文会发给服务提供方；PDF OCR 可能向 DashScope 发送页面图像。使用真实资料或外部服务时，按当前用户指令与适用权限处理。
- 本地依赖、模型、配置和运行数据可能不随 Git worktree 复制。启动和验证方法以 [README](../README.md) 及当前环境为准；不要把健康检查当作模型与完整问答链路已验证。
